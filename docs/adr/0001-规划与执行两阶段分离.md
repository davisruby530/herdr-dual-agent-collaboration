# 规划与执行两阶段分离，执行阶段由 /goal 驱动单 Coder

原 `AGENTS.md` 把两大铁律的适用范围写成"所有方案设计、开发……工作"，并把 Spec 当作 Principal 给定的外部输入；结果团队用 grill-with-docs 起步时，agent 先要求提供 Spec，而 Spec 恰恰要靠 grill → to-spec 才能产出，形成死锁。我们决定把协作切成两段：**规划阶段**（grill-with-docs → to-spec → to-tickets，Principal 与单个 agent 对话，不建工单、不提审、铁律不适用）与**执行阶段**（铁律生效）；两段的交接点是 Principal 批准 to-tickets 的拆分方案。执行阶段由 `/goal` 驱动 Coder 自主推进，但单个 Coder 同时只处理一张工单，提审后在一次工具调用内阻塞等待 Reviewer 裁决（`scripts/wait-for-verdict.sh`），不利用可开工集并行。

## Considered Options

- **铁律覆盖全流程，把 grill/to-spec 也做成工单提审**：被否决。规划是与 Principal 的对话，Reviewer 无从"沙箱复验"一段访谈，只会制造空转的提审。
- **使用 `implement-spec` 并行执行**：被否决。它以自带的 code-review 收尾并自动关单，绕过 Reviewer，违反"严禁擅自闭环"。
- **提审后 Coder 继续开下一张可开工工单**：暂不采用。goal 续跑最大的风险就是"等待"被打断后 agent 自行推进；单线程让 Reviewer 意见不与其他工单改动交织。多 Coder 窗格时可重新评估。

## Consequences

- 不要把铁律适用范围改回"所有方案设计"——那会重新引入本次死锁。
- `implement`、`to-spec`、`to-tickets` 均为 `disable-model-invocation`，goal 模式下 Coder 无法自行调用，所以单张工单的执行步骤写在 `AGENTS.md` 里，而非依赖 `/implement`。
- Spec 缺陷需要一条回到规划阶段的回路（上报 → 修订 Spec → 局部重出工单 → 旧工单 `superseded`）。重出工单时要从现有最大编号加 1 开始，否则 `/to-tickets` 从 01 编号会覆盖旧工单。
- **不要把等待改回"结束回合"。** 最初版本就是这样设计的，但 Claude Code 的 `/goal` 用 Stop hook 实现，每轮结束后只要目标未达成就会让 agent 继续，结束回合等于空转。同理，goal 的完成条件必须包含"或已上报"。
